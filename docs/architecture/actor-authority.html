Actor identity, authority, and cell travel

How one NPC stays the same NPC while clients load and unload cells, players trade simulation responsibility, and the server resets a live world.

Applies to the experimental/public-test actor-sync v2 implementation through 8ff5998dc4 (October 2026). This chapter documents implementation behavior, not a stable public protocol.

1. The mental model

The server owns the canonical identity and shared state of a multiplayer actor. A selected client runs the OpenMW AI and physics for that actor and reports updates. Other clients bind the same network identity to local engine objects and render it as an observer. The server validates who may publish; it does not run a second copy of OpenMW's NPC AI.

Four different questions: Who is this actor? Where is its canonical cell? Which client may simulate it? Which clients currently have it loaded? The answers live in different fields and can change independently.

For example, Mario may publish EXT:-3,-2 while Sith continues to simulate a walker there. Crossing into EXT:-2,-2 moves that walker's spatial index entry. Neither event alone requires an actor-authority transfer.

The earlier failure pattern came from conflating these questions: losing an origin cell could lose the actor's state, a new cell publisher could take over too early, and an observer's local leveled roll could survive beside a different canonical actor. The recent work separates identity, spatial membership, simulation lease, and presentation, then gives each transition its own generation or explicit removal reason.

2. Identity is independent of location

ActorInstanceId is a 64-bit value derived from an ActorInstanceKey. Its high part encodes the key kind; its low 32 bits carry either the content-qualified vanilla refNum or a server-assigned spawned mpNum. A spawned actor can have a temporary engine ref number locally, but its multiplayer identity remains its mpNum. The console's local 97-0 notation is useful for investigation; it is not the actor's portable network key.

vanilla placed actor → (VanillaRefNum, FormId32 refNum) → ActorInstanceId
server-spawned actor → (SpawnedMpNum, mpNum)        → ActorInstanceId
cell or owner change → same ActorInstanceId

Two monotonically advancing epochs protect that stable ID. migrationGeneration advances when the canonical actor moves to another cell. actorAuthorityGeneration advances when its simulation lease changes or is revoked. A cell publisher has a separate CellActorState::authorityGeneration. Do not substitute one generation for another: a packet can be current for ownership but stale for physical location.

The server retains generation high-water maps for actors recreated after an incomplete roster or reset-related repair. The client rejects older migrations and leases, and buffers a small number of position snapshots that arrive before the matching reliable cell-change commit. This prevents late packets from moving an actor back across a border or resurrecting an old simulator.

3. One canonical record, several indexes

Server

WorldState::actorsByNetId is the primary unordered_map<ActorInstanceId, shared_ptr<ActorRegistryRecord>>. A registry record contains the current BaseActor snapshot plus lease, migration, death, combat replay, crime, persistence, and temporary-spell state. actorCells[cellId].actors is a spatial bucket of shared pointers to those same records; actorLocations accelerates location lookup. A cell is therefore an index, not the lifetime owner of an exterior actor.

WorldState
├─ actorsByNetId[id] ─────────────┐  primary identity / lifetime
├─ actorLocations[key] → cellId   │  location hint
└─ actorCells[cellId].actors[key] ─┴→ same ActorRegistryRecord
                         (not a second copy of AI or lease state)

On migration, the server extracts the map node from the old cell bucket and inserts it into the destination bucket. It updates the record's canonical cell and migration generation without reconstructing the record. A stale duplicate bucket is removed; the global record wins even if the duplicate has a newer-looking snapshot. findActorByNetId resolves through the global map first, so an index that briefly lags cannot make a live actor disappear.

Exterior actors remain registered when the last cell publisher leaves. Interior nonpersistent runtime spawns still have their existing cell-scoped cleanup behavior. Persistence is separate again: durable spawned actors, dead vanilla actors, disposed corpses, and related world state live in the database, while ordinary session state lives in memory.

Client

ActorSync::mActorsByNetId is the primary runtime map. An ActorRuntime joins a canonical BaseActor snapshot to a bound MWWorld::Ptr, migration epoch, interpolation queue, presentation state, and cell-handoff bookkeeping. mCells[cellId] holds cell-local packet state and provisional actors. Once identity is known, packet handling resolves the primary runtime first. Redundant observer shadows are pruned instead of becoming competing actor copies.

The engine Ptr and the network ID are deliberately distinct. A leveled-list child can resolve to a different local creature on another client; mReconciledVanillaActorsByNetId binds the authoritative placed-spawner ID to that client's replacement Ptr. A server-spawned actor has an additional mpNum → Ptr map to recover its binding after streaming. Neither map is a second source of actor identity.

When adding a new actor field: decide whether it belongs to canonical BaseActor, server-only registry metadata, client-only presentation, or durable database state. Putting it only in a cell bucket makes it vulnerable to migration and unload.

4. Choosing who simulates

The server still elects a cell publisher to seed complete cell rosters. Exterior eligibility is a configurable square grid radius (currently one cell). A brief sticky window (currently 3 seconds), exact-cell preference, nearest-grid selection, and stable GUID tie-breaks limit cell-publisher churn. Per-actor simulation is a separate lease for live registered actors; corpses and player avatars do not acquire it. Explicit script-owner authority is preserved.

A capable actor owner stays in place through a border, AI package change, Follow/Escort transition, or combat-target switch. “Capable” means it can simulate the actor's coordinates inside its active AI bounds and, for a live player target, also has that target within its eligible cell horizon. The actor-position check uses a 200-unit edge margin for retaining an owner. A replacement candidate needs 512 units of room, giving Ready/Commit time before it reaches OpenMW's inactive-cell pathfinding limit.

Only after the owner loses that capability does the server choose a candidate. It filters connected v2 clients by actor position and target coverage, then prefers an independent simulator over the combat victim when one is available; distance and GUID resolve the rest. Thus a nearby bystander can simulate an NPC without becoming its combat target. The server also preserves canonical combat when an owner's local target proxy leaves its horizon; the client cannot silently publish “idle” merely because that proxy unloaded.

If no client can cover both an ownerless actor and its distant combat victim, the server waits briefly (currently 5 seconds). It then abandons only the unreachable chase, retaining any reachable hostile player targets, and retries transfer so the actor can idle, return, or acquire a legitimate nearby target. This avoids both a permanent freeze and an unjustified attack on an innocent player.

5. A prepared transfer, not an optimistic owner flip

1 · PrepareServer selects candidate and sends canonical actor state, generations, location, and timed effects.
2 · ReadyCandidate verifies its actor and combat target are active scene objects it can actually simulate.
3 · CommitServer revalidates, sends a fresh final snapshot, changes the lease, and broadcasts its generation.
4 · AppliedCandidate installs the snapshot before its first AI tick and acknowledges successful promotion.

ActorAuthorityTransfer carries actorNetId, a unique transferId, old/new owner GUIDs, authority and migration generations, canonical cell, actor snapshot, and timed active spells. Ready and Commit must match this transaction exactly. The client does not send Ready merely because it has an identity record: the bound actor needs an active cell and scene node, and a combat target needs a live scene node too. A narrow border exception permits a vanilla actor already in the neighboring CellStore while a reliable migration commit is still in flight.

During preparation, the old lease remains valid. Immediately before Commit, the server refreshes the canonical snapshot so movement made by the old owner during the handshake is not lost. On promotion the new owner moves its gameplay Ptr to that committed transform, clears obsolete observer interpolation, restores AI and timed spells, then emits Applied. Duplicate or delayed Prepare messages cannot replace a newer generation or re-gate a committed owner. Cancel aborts an obsolete proposal; Available/Unavailable reports let a current simulator tell the server its scene actor appeared or vanished.

The server checks waiting transfers periodically. If a candidate is not Ready after 5 seconds, it tries another eligible candidate once; if none exists, it leaves the proposal pending for the original scene to load. If Commit receives no Applied acknowledgment in time, the server revokes that lease and retries. Every regular actor update is validated against the current lease so a former owner cannot keep writing after Commit.

6. Physical border crossing versus authority handoff

A moving actor crossing an exterior grid line triggers a reliable ActorCellChange from its authorized source. The server validates destination eligibility and actor identity, rejects stale reverse crossings, advances migrationGeneration, moves the same registry pointer between spatial buckets, updates location and persistence links, and sends the migration to interested clients. An ordinary position packet does not get to invent a new canonical cell while that reliable path is available.

Position, animation, and attacks travel on different lanes. Compact ActorPositionV2 snapshots carry position, velocity, animation speed, and locomotion axes; presentation snapshots carry animation state; attack events are reliable and deduplicated. Identity must be known before compact snapshots can be applied. Future-generation positions can wait briefly for the reliable migration packet rather than being discarded or interpreted in the old cell.

Canonical location and rendered location need not advance on the same frame. The observer keeps a bound actor in its already-loaded source CellStore until the interpolated position has visually crossed the seam. Rebinding the engine object exactly at the line used to rebuild scene and mechanics state, producing a visible stall. On a simulator handoff, the promoted client's outgoing network position can use a short, bounded offset bridge so observers do not see a backward snap from its delayed puppet position. The gameplay Ptr still starts from Commit's canonical transform; presentation continuity does not authorize old movement.

The handoff helpers cap prediction after a delayed stream, expire stale locomotion, and guard against immediate reverse migration. These are presentation and ordering controls around a single canonical actor, not a second movement simulation.

7. Complete rosters reconcile local OpenMW rolls

A cell publisher may send an ActorList; the server converts its accepted records into reliable ActorIdentityList baselines. completeCellSnapshot is set only after a genuinely complete publisher roster. A startup overlay of persistent corpses, for example, is not enough evidence to delete local actors. Clients acknowledge identities and then resolve compact movement by actorNetId.

Leveled creature spawners are particularly dangerous: two clients can roll different children, or one can roll “Chance None.” Once a complete authoritative roster arrives, observers bind the authoritative spawner identity to the local child, remove extra local rolls, or preserve the authoritative empty result. If the roster arrives before scene insertion, the client saves it and reconciles before the cell renders. Corpse-disposal tombstones likewise survive unload/reload so a local reroll cannot recreate a disposed actor.

A migrated actor absent from its old origin roster is not evidence of death or despawn. Migration generation, canonical cell, and primary runtime take precedence over an old cell's membership list. Explicit removal reasons distinguish ordinary despawn, cell reset, and corpse disposal. That distinction fixed stationary client-only extras, missing observers, and actors that appeared only after another player crossed a border.

8. Live cell reset is an invalidation barrier

/resetcell and /resetallcells intentionally replace world state; walking away does not. The server first builds a per-cell reset plan, then deletes persisted world rows in one SQLite BEGIN IMMEDIATE transaction. If that transaction fails, it rolls back and does not mutate the runtime. Once it succeeds, the server clears the selected cells' actor indexes and related objects, containers, doors, deaths, and disposals, advances each cell-authority generation, and removes corresponding global actor IDs.

Publishing the reset is just as important as deleting the rows. The server sends explicit actor identity removals with ActorRemovalReason::CellReset, an empty actor list, object deletions, restored door baselines, and a container Reset packet to every connected selected client—including clients that visited a cell earlier but are no longer beside it. The old cell publisher is revoked, and the server elects a fresh one to seed the base state. Generation changes reject stale in-flight writes from before the reset.

Clients clear primary runtimes, mpNum bindings, authority caches, reconciled leveled children, and cached cell state. An active cell is reset immediately; an unloaded cell is marked pending and reset before its next scene insertion. Only the new authority rerolls leveled spawners. Observers wait for the canonical roster rather than creating independent zombies. No relog is required to see a correct live reset.

Do not implement reset as “clear the current cell map.” That misses the global registry, old client CellStores, persisted rows, generations, and local leveled rolls. The full operation is a coordinated database, runtime, and network barrier.

9. State that must survive a new simulator

The actor record retains canonical AI and its set of hostile player targets, so changing simulator does not implicitly redirect combat to the new owner. A disconnected target is cleared; a connected target outside every possible simulator's horizon can be abandoned after the grace period described above. Attack-event IDs and replay guards prevent a handoff from replaying a hit. Observer animation is presentation, not proof that an attack landed.

Temporary magic needs more than a movement-speed number. The owner reports ESM::ActiveSpells in mechanics snapshots; the server caches that state independently of cell rosters and ages its remaining durations before Prepare and again before Commit. The new simulator installs already-rolled effects before AI resumes. Transfer flags prevent a second resistance, reflection, or absorption roll. Lasting Fortify Attribute modifiers are deliberately applied once on promotion, while unrelated one-shot effects such as damage or teleportation are not replayed. This is why Fortify Speed can remain effective across owner disconnect and cell unload until its real timer expires.

Spell cast events and projectiles have their own replication paths; a correct actor lease alone does not guarantee that an observer sees a bolt or a hit VFX. When investigating “swinging but no projectile,” inspect both the actor's AI/lease and the cast-event path.

10. Debugging from invariants

Start with the actorNetId, not the screen position or a client's console index. For any suspicious actor, reconstruct this chain:

  1. Does actorsByNetId[id] exist, and is the cell bucket pointing to the same record?
  2. Do the actor's canonical cell and migrationGeneration match the latest accepted ActorCellChange?
  3. Which GUID holds actorAuthorityGeneration? Is there a pending Prepare, a Ready, or an unacknowledged Commit?
  4. Does that client's primary runtime have a live bound Ptr, active cell, and (for Combat/Pursue) an active target?
  5. Did both observers receive and acknowledge identity before compact positions or presentation?
  6. Was an actor explicitly removed, reset, disposed, or merely omitted from an old cell roster?

Typical signatures: freezes at a border suggest the simulator lost its scene actor or a destination was never Ready; backward wiggles suggest canonical movement and delayed observer interpolation were mixed; one-client-only extras suggest stale local leveled rolls or a missing complete-roster cleanup; effects disappearing at handoff suggest a stale timed-spell snapshot or effect flags that prevented installation. Distinguish these before changing interpolation or widening rendering distance.

The focused regression surface includes identity packing, generation ordering, border presentation, transfer matching, and reset behavior. Follow it with two-client tests involving origin unload, return travel, disconnect, relog, and a live /resetallcells. Long sessions still matter: a passing one-border test does not exercise stale packets, delayed scene insertion, or cell-memory reuse.
